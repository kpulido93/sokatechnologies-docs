## 1. Objetivo del proceso de entrega

El objetivo de este proceso es definir cómo SokaTechnologies ejecuta proyectos desde la aprobación comercial hasta la entrega formal, soporte y mejora continua.

Este proceso busca:

- Entregar proyectos con orden, aunque la empresa sea operada por una sola persona.
- Reducir retrabajo causado por requerimientos ambiguos.
- Proteger tiempo, margen y flujo de caja.
- Mantener comunicación clara con el cliente.
- Documentar decisiones, entregables, cambios y aprobaciones.
- Evitar despliegues improvisados o inseguros.
- Convertir entregas puntuales en relaciones recurrentes de soporte mensual.
- Preparar la operación para delegar tareas a freelancers o empleados en el futuro.

Este proceso aplica a proyectos de:

- Software a medida.
- Sitios web corporativos.
- Automatizaciones.
- Integraciones entre sistemas.
- Dashboards y reportes.
- Infraestructura cloud/on-prem.
- Soporte, mantenimiento y mejoras continuas.

La regla central es:

> Nada se construye sin alcance claro, nada se despliega sin pruebas y backup, nada se cierra sin documentación, y todo proyecto debe ofrecer una ruta hacia soporte mensual.

## 2. Principios operativos

SokaTechnologies debe mantener un proceso simple, práctico y repetible. No se debe crear burocracia innecesaria, pero sí controles mínimos que protejan la operación.

| Principio | Regla práctica |
|---|---|
| Claridad antes de construir | No iniciar desarrollo sin requerimientos y alcance definidos. |
| Pago antes de ejecución | No iniciar proyecto sin anticipo o condición comercial aprobada. |
| Comunicación documentada | Las decisiones importantes deben quedar por escrito. |
| Entregas por hitos | Dividir el proyecto en avances pequeños y verificables. |
| Seguridad desde el inicio | No usar datos sensibles innecesarios ni guardar secretos en repositorios. |
| Cambios controlados | Todo cambio fuera de alcance se evalúa como ajuste, mejora o nueva fase. |
| Documentación mínima útil | Todo proyecto debe poder mantenerse sin depender solo de memoria. |
| Soporte recurrente | Toda entrega debe terminar con una propuesta de soporte o mantenimiento. |

## 3. Flujo completo de entrega

El flujo completo inicia cuando el cliente acepta una propuesta comercial y termina cuando el proyecto queda cerrado o convertido en soporte mensual.

| # | Etapa | Objetivo | Resultado esperado |
|---:|---|---|---|
| 1 | Propuesta aceptada | Confirmar que el cliente aprobó la solución, precio y condiciones. | Propuesta aprobada por escrito. |
| 2 | Contrato o acuerdo | Formalizar responsabilidades, alcance general y condiciones. | Contrato, orden de compra, correo de aprobación o acuerdo firmado. |
| 3 | Anticipo | Asegurar compromiso y flujo de caja antes de iniciar. | Pago inicial recibido o confirmado según acuerdo. |
| 4 | Onboarding | Preparar estructura, accesos, canales y reglas de trabajo. | Proyecto creado y listo para kickoff. |
| 5 | Kickoff | Alinear expectativas, responsables, fechas y forma de trabajo. | Minuta de kickoff y próximos pasos confirmados. |
| 6 | Levantamiento de requerimientos | Entender procesos, usuarios, datos, reglas e integraciones. | Documento de requerimientos. |
| 7 | Alcance final | Definir qué se entrega, qué no se entrega y cómo se aprobará. | Alcance aprobado. |
| 8 | Diseño funcional | Describir cómo funcionará la solución desde la perspectiva del usuario. | Flujos, pantallas, reportes, reglas o prototipo simple. |
| 9 | Diseño técnico | Definir arquitectura, datos, seguridad, infraestructura y despliegue. | Diseño técnico mínimo. |
| 10 | Desarrollo | Construir la solución por módulos o entregables. | Funcionalidades listas para revisión interna. |
| 11 | QA | Probar funcionalidad, datos, permisos, seguridad básica e integraciones. | Checklist QA completado. |
| 12 | Demo | Mostrar avance funcional al cliente. | Feedback documentado. |
| 13 | Ajustes | Corregir errores o ajustes incluidos dentro del alcance aprobado. | Versión validada para despliegue. |
| 14 | Despliegue | Publicar la solución en el ambiente acordado. | Sistema, sitio, automatización o infraestructura operativa. |
| 15 | Capacitación | Enseñar uso básico y reglas operativas. | Sesión de capacitación y guía de uso. |
| 16 | Entrega formal | Confirmar que el alcance fue entregado. | Acta, correo o documento de entrega. |
| 17 | Garantía | Corregir errores cubiertos por el alcance original. | Incidentes de garantía resueltos. |
| 18 | Soporte | Mantener, monitorear y mejorar la solución. | Plan mensual o bolsa de horas activa. |
| 19 | Mejora continua | Convertir necesidades futuras en backlog o nuevas fases. | Roadmap de mejoras priorizado. |

## 4. Roles en una empresa de una sola persona

Actualmente SokaTechnologies no debe asumir que existe un project manager. El fundador cumple varios roles, pero debe separar mentalmente las responsabilidades para evitar desorden.

| Rol operativo | Responsable actual | Función |
|---|---|---|
| Responsable comercial | Fundador | Alinear propuesta, precio, pagos y condiciones. |
| Responsable funcional | Fundador | Entender procesos, usuarios, reglas y entregables. |
| Responsable técnico | Fundador | Diseñar arquitectura, desarrollo, seguridad y despliegue. |
| Responsable QA | Fundador | Validar que el entregable funcione antes de mostrarlo. |
| Responsable de soporte | Fundador | Atender garantía, soporte mensual y mejoras. |
| Cliente aprobador | Persona designada por el cliente | Aprobar requerimientos, alcance, demos y entrega. |

Regla práctica:

> Aunque una sola persona ejecute todo, cada decisión debe quedar registrada como si mañana otra persona tuviera que continuar el proyecto.

- No usar datos reales en demos públicas o material comercial sin autorización.

## 6. Checklist de kickoff

La reunión de kickoff debe ser corta y práctica. Su objetivo no es resolver todo, sino alinear expectativas y confirmar cómo se trabajará.

### Objetivos del kickoff

- Confirmar el objetivo de negocio del proyecto.
- Revisar alcance general aprobado.
- Confirmar responsables y canal de comunicación.
- Acordar fechas clave.
- Identificar accesos, insumos y dependencias del cliente.
- Explicar cómo se manejarán cambios, retrasos y aprobaciones.

### Agenda sugerida

| Tema | Preguntas clave |
|---|---|
| Contexto | ¿Qué problema se busca resolver? |
| Resultado esperado | ¿Cómo sabremos que el proyecto fue exitoso? |

| Exclusiones | ¿Qué no está incluido? |
| Responsables | ¿Quién aprueba y quién entrega información? |
| Comunicación | ¿Dónde se reportan avances y dudas? |
| Fechas | ¿Qué hitos son críticos? |
| Accesos | ¿Qué credenciales, sistemas o archivos se necesitan? |
| Riesgos | ¿Qué podría bloquear el proyecto? |
| Próximos pasos | ¿Qué debe pasar antes del levantamiento detallado? |

## 9. Criterios de aceptación

Los criterios de aceptación definen cómo se determina que una funcionalidad, módulo o proyecto está terminado.

Deben ser claros, verificables y entendibles para el cliente.

### Tipos de criterios

| Tipo | Ejemplo |
|---|---|
| Funcional | El usuario puede crear, editar, consultar o eliminar registros según su rol. |
| Datos | Los cálculos, filtros y reportes muestran información correcta. |
| Permisos | Cada rol solo ve y modifica lo que le corresponde. |
| Integración | El sistema externo recibe o envía datos correctamente. |
| Seguridad | No se exponen datos sensibles ni accesos no autorizados. |
| Despliegue | La solución funciona en el ambiente acordado. |
| Documentación | El cliente recibe instrucciones mínimas de uso y operación. |

### Formato recomendado

```md
## Criterio de aceptación

Dado que [contexto o rol],
cuando [acción o evento],
entonces [resultado esperado].
```

Ejemplo:

```md
Dado que un usuario operativo inició sesión,
cuando registra un nuevo caso con todos los campos obligatorios,
entonces el sistema guarda el caso, muestra confirmación y permite consultarlo en el listado correspondiente.
```

### Checklist de criterios de aceptación

| Ítem | Estado |
|---|---|
| Cada funcionalidad principal tiene criterio de aceptación. | [ ] |
| Los reportes tienen filtros y resultados esperados definidos. | [ ] |
| Los roles y permisos están definidos. | [ ] |
| Las integraciones tienen comportamiento esperado definido. | [ ] |
| Los casos de error principales están contemplados. | [ ] |
| El cliente aprobó los criterios antes del desarrollo principal. | [ ] |

## 10. Diseño funcional

El diseño funcional explica cómo se verá y se comportará la solución desde el punto de vista del usuario.

No siempre requiere diseños visuales avanzados. Para una empresa pequeña, puede bastar con flujos, pantallas simples, wireframes, tablas o descripciones claras.

### Debe incluir

- Flujos principales.
- Pantallas o vistas principales.
- Formularios y campos importantes.
- Estados del proceso.
- Roles que usan cada función.
- Reportes y filtros.
- Notificaciones o alertas.
- Reglas de negocio visibles para el usuario.

### Ejemplo de flujo funcional

```md
## Flujo: Registro de solicitud

1. Usuario ingresa al sistema.
2. Selecciona "Nueva solicitud".
3. Completa campos obligatorios.
4. Adjunta evidencia, si aplica.
5. Envía la solicitud.
6. El sistema asigna estado "Pendiente".
7. El supervisor recibe notificación o puede verla en su bandeja.
8. El supervisor aprueba, rechaza o solicita corrección.
```

## 11. Diseño técnico

El diseño técnico define cómo se construirá, desplegará y mantendrá la solución.

Debe ser suficientemente claro para que el fundador pueda mantener el proyecto y para que en el futuro un freelancer o empleado pueda entenderlo.

### Debe incluir

- Arquitectura general.
- Stack tecnológico.
- Estructura de carpetas.
- Modelo de datos inicial.
- Endpoints o interfaces principales, si aplica.
- Integraciones externas.
- Variables de entorno.
- Estrategia de autenticación y permisos.
- Manejo de archivos, si aplica.
- Logs y monitoreo.
- Backup y restauración.
- Ambientes: desarrollo, pruebas, producción.
- Proceso de despliegue.
- Riesgos técnicos.

### Checklist de diseño técnico

| Ítem | Estado |
|---|---|

| Stack tecnológico definido. | [ ] |

### Buenas prácticas de seguridad

- No guardar contraseñas, tokens, claves privadas o secretos en Git.
- Usar variables de entorno.
- Mantener `.env.example` sin valores reales.
- Validar entradas de usuario.
- Aplicar roles y permisos cuando exista información sensible.
- Usar HTTPS cuando aplique.
- Realizar backup antes de cambios importantes.
- Evitar exponer servicios internos innecesariamente.
- Usar datos ficticios en demos comerciales.
- Rotar credenciales si se sospecha exposición.

## 12. Desarrollo

El desarrollo debe organizarse por tareas pequeñas, no por bloques grandes difíciles de revisar.

### Flujo de desarrollo recomendado

1. Crear tarea con objetivo y criterio de aceptación.
2. Crear rama o separar cambios por funcionalidad, si aplica.
3. Implementar la funcionalidad.
4. Ejecutar pruebas locales.
5. Revisar cambios antes de integrar.
6. Actualizar documentación si el cambio lo requiere.
7. Preparar demo interna.
8. Pasar a QA.

## 13. Uso de Codex durante la entrega

Codex puede acelerar desarrollo, pruebas, documentación y mantenimiento, pero debe usarse con control.

### Usos recomendados

| Etapa | Uso de Codex |
|---|---|
| Requerimientos | Convertir notas en historias de usuario o criterios de aceptación. |
| Diseño técnico | Proponer estructura de carpetas, endpoints o modelo inicial. |
| Desarrollo | Implementar tareas pequeñas y bien definidas. |
| QA | Sugerir casos de prueba, revisar validaciones y detectar riesgos. |
| Documentación | Crear README, release notes, guías de uso o checklist. |
| Soporte | Ayudar a diagnosticar bugs con logs anonimizados. |

### Reglas obligatorias

- Codex no debe tocar producción directamente.
- Codex no debe recibir secretos, tokens, contraseñas ni datos sensibles.
- Codex no debe hacer cambios masivos sin plan previo.
- Todo cambio generado debe revisarse mediante diff o pull request.
- Todo cambio debe probarse antes de integrarse.
- Si Codex modifica archivos no relacionados, se debe rechazar o corregir.
- El fundador conserva la responsabilidad técnica final.

### Prompt recomendado para Codex

```md
## Tarea para Codex

### Objetivo
Describe exactamente qué se debe construir, corregir o documentar.

### Contexto
Explica brevemente el proyecto y por qué se necesita el cambio.

### Archivos relevantes
- `ruta/archivo1`
- `ruta/archivo2`

### Restricciones
- No tocar producción.
- No agregar secretos.
- No modificar archivos fuera del alcance sin justificar.
- No cambiar el modelo de datos sin propuesta previa.
- No agregar dependencias nuevas sin explicar por qué.

### Criterios de aceptación
- [ ] Criterio 1.
- [ ] Criterio 2.
- [ ] Criterio 3.

### Comandos de prueba
- `npm test`
- `npm run lint`
- Otro comando según el proyecto.

### Entrega esperada
- Resumen de cambios.
- Archivos modificados.
- Riesgos o decisiones técnicas.
```

## 14. QA y pruebas

QA es la validación interna antes de mostrar o entregar al cliente.

Para una empresa de una sola persona, QA debe ser simple pero obligatorio.

### Tipos de prueba

| Tipo | Qué valida |
|---|---|
| Funcional | La solución hace lo solicitado. |
| Datos | Cálculos, reportes, filtros y exportaciones son correctos. |
| Permisos | Cada rol accede solo a lo permitido. |
| Integración | APIs, archivos o sistemas externos funcionan. |
| Visual | Pantallas clave son usables y consistentes. |
| Regresión | Cambios nuevos no rompen funciones existentes. |
| Seguridad básica | No hay exposición obvia de datos, secretos o paneles. |
| Despliegue | La solución funciona en el ambiente objetivo. |

### Checklist QA

| Ítem | Estado |
|---|---|
| Funcionalidades principales probadas. | [ ] |
| Casos de error principales probados. | [ ] |

| Reportes y filtros revisados. | [ ] |
| Integraciones probadas. | [ ] |
| Logs revisados. | [ ] |
| Pruebas automatizadas ejecutadas, si existen. | [ ] |
| Build ejecutado, si aplica. | [ ] |
| No hay secretos en el repositorio. | [ ] |
| Bugs críticos corregidos antes de demo. | [ ] |

### Clasificación de bugs

| Severidad | Descripción | Acción |
|---|---|---|
| Crítico | Bloquea operación, acceso o datos importantes. | Corregir antes de entregar. |
| Alto | Afecta una función importante, pero existe alternativa temporal. | Corregir antes de producción o acordar fecha. |
| Medio | Afecta comodidad o caso secundario. | Puede pasar a backlog si el cliente aprueba. |
| Bajo | Visual, texto, mejora menor o ajuste no crítico. | Puede resolverse en ajuste o soporte. |

### Objetivo de la demo

- Mostrar funcionalidad real.

## 16. Ajustes

Después de una demo o revisión, los ajustes deben clasificarse correctamente.

| Tipo | Tratamiento |
|---|---|
| Bug | Se corrige si la funcionalidad no cumple el alcance aprobado. |
| Ajuste menor | Se realiza si está dentro del alcance y no afecta costo o fecha. |
| Cambio fuera de alcance | Se gestiona mediante control de cambios. |
| Mejora futura | Se registra en backlog o propuesta de soporte mensual. |
| Nueva fase | Se cotiza como proyecto adicional. |

Regla práctica:

> No todo feedback del cliente es un bug. Primero se clasifica, luego se decide si se corrige, se agenda o se cotiza.

## 17. Control de cambios

El control de cambios protege margen, fechas y claridad.

Debe usarse cuando el cliente solicite algo que no está en el alcance aprobado.

### Ejemplos de cambios

- Nueva funcionalidad.
- Nuevo reporte.
- Nueva integración.
- Cambio importante de flujo.
- Nueva pantalla o módulo.
- Cambio de diseño no contemplado.
- Automatización adicional.
- Cambio de infraestructura.
- Modificación posterior a aprobación de UAT.

### Flujo de control de cambios

1. Cliente solicita cambio.
2. Se registra la solicitud.
3. Se evalúa impacto en tiempo, costo, riesgo y alcance.
4. Se clasifica como ajuste incluido, mejora, nueva fase o cambio facturable.
5. Se envía estimación o propuesta breve.
6. Cliente aprueba por escrito.
7. Se agenda y ejecuta.
8. Se actualiza documentación y cierre.

## Impacto estimado

## 18. Manejo de cambios fuera de alcance

Los cambios fuera de alcance deben tratarse con claridad y sin conflicto.

### Respuesta recomendada al cliente

```md
Gracias por la solicitud. Lo revisé y este punto no estaba incluido en el alcance aprobado originalmente.

Puedo manejarlo de una de estas formas:

1. Lo dejamos como mejora para una siguiente fase.
2. Lo cotizo como cambio adicional.
3. Lo incluimos dentro de un plan de soporte mensual o bolsa de horas, si aplica.

Para avanzar, prepararé una estimación breve de impacto en tiempo, costo y fecha.
```

### Reglas internas

- No rechazar de forma brusca; clasificar y ofrecer alternativa.
- No hacer cambios grandes gratis para “mantener feliz” al cliente.
- No intercambiar precio sin ajustar alcance.
- No ejecutar cambios fuera de alcance sin aprobación escrita.
- Registrar cada cambio en la carpeta del proyecto.

## 19. Manejo de retrasos causados por el cliente

Muchos retrasos ocurren porque el cliente no entrega información, accesos, aprobaciones o feedback a tiempo.

Este proceso evita que esos retrasos se conviertan en responsabilidad de SokaTechnologies.

### Causas comunes

- El cliente no entrega accesos.
- El cliente no responde dudas funcionales.
- El cliente no aprueba requerimientos o demo.
- El cliente cambia responsables internos.
- El cliente entrega información incompleta o incorrecta.
- El cliente retrasa pagos acordados.
- El cliente pide pausar sin definir nueva fecha.

### Regla operativa

Si una dependencia del cliente bloquea el proyecto, el cronograma se mueve proporcionalmente.

### Flujo de manejo de retrasos

1. Registrar bloqueo.
2. Enviar recordatorio amable con fecha y pendiente específico.
3. Si no responde, enviar segundo recordatorio indicando impacto en fecha.
4. Si continúa bloqueado, pausar proyecto formalmente.
5. Reprogramar cuando el cliente entregue lo pendiente.
6. Si la pausa genera retrabajo o reactivación, evaluar costo adicional.

### Plantilla de aviso de bloqueo

```md
Hola [Nombre],

Para avanzar con [actividad/hito], necesitamos recibir [insumo/acceso/aprobación].

Mientras esto esté pendiente, el proyecto queda bloqueado en esta etapa y la fecha de entrega puede moverse según el tiempo de respuesta.

Pendiente requerido:
- [Pendiente]

Fecha ideal de respuesta:
- [Fecha]

Quedo atento para continuar.
```

### Plantilla de pausa por falta de respuesta

```md
Hola [Nombre],

Como aún está pendiente [insumo/acceso/aprobación], dejaremos el proyecto en pausa temporal hasta recibir esta información.

Cuando esté disponible, revisaremos la nueva fecha de continuación según la agenda activa y el impacto acumulado.

Esto ayuda a mantener claridad sobre tiempos, prioridades y responsabilidades.
```

## 24. Garantía

La garantía cubre correcciones de errores relacionados con el alcance aprobado.

No debe confundirse con soporte ilimitado ni con desarrollo de nuevas funcionalidades.

### Cubre

- Bugs de funcionalidades incluidas.
- Errores de configuración causados por la entrega.
- Ajustes necesarios para que lo aprobado funcione correctamente.

### No cubre

- Nuevas funcionalidades.
- Cambios de proceso del cliente.
- Nuevos reportes.
- Nuevas integraciones.
- Cambios de diseño no aprobados previamente.
- Problemas causados por terceros, hosting externo o credenciales modificadas.
- Soporte operativo recurrente.
- Capacitación adicional no acordada.
- Cambios posteriores en APIs o plataformas externas.

### Recomendación

Definir el período de garantía en la propuesta o contrato. Para proyectos pequeños, puede ser de 15 a 30 días. Para proyectos más grandes, puede variar según acuerdo comercial.

Validar condiciones legales, fiscales y contractuales con un asesor según el país del cliente.

## 25. Soporte mensual

El soporte mensual permite convertir una entrega puntual en una relación recurrente.

### Objetivo del soporte

- Mantener la solución funcionando.
- Corregir incidentes menores.
- Monitorear errores o disponibilidad, si aplica.
- Realizar backups o verificaciones periódicas.
- Atender dudas operativas.
- Ejecutar mejoras pequeñas.
- Planificar nuevas fases.

### Tipos de soporte

| Tipo | Descripción |
|---|---|
| Correctivo | Corrección de errores. |
| Preventivo | Backups, actualizaciones, monitoreo y revisiones. |
| Operativo | Ayuda de uso, pequeñas configuraciones y consultas. |
| Evolutivo | Mejoras, nuevos reportes o pequeños cambios. |
| Infraestructura | Servidores, dominios, SSL, bases de datos y despliegues. |

### Planes sugeridos

| Plan | Enfoque | Incluye |
|---|---|---|
| Básico | Sitios web o sistemas pequeños. | Revisión mensual, soporte limitado, backups básicos si aplica. |
| Operativo | Sistemas usados por el negocio. | Bolsa de horas, soporte priorizado, ajustes menores y reporte mensual. |
| Evolutivo | Clientes con mejoras frecuentes. | Bolsa mayor de horas, roadmap, mejoras continuas y seguimiento recurrente. |

Evitar prometer soporte 24/7 si SokaTechnologies todavía opera con una sola persona. Si un cliente requiere alta disponibilidad, se debe cotizar aparte con condiciones específicas.

## 32. Riesgos principales y mitigación

| Riesgo | Impacto | Mitigación |
|---|---|---|
| Iniciar sin alcance claro | Retrabajo y pérdida de margen. | Requerimientos y alcance final aprobados. |
| Cliente pide cambios constantes | Retraso y trabajo no cobrado. | Control de cambios. |
| Cliente no responde | Cronograma bloqueado. | Proceso de retrasos causados por cliente. |
| Despliegue apresurado | Fallos en producción. | Checklist antes de producción. |
| Falta de backup | Pérdida de datos. | Backup antes de cambios críticos. |
| Secretos expuestos | Riesgo de seguridad. | Variables de entorno y revisión de repositorio. |
| Uso descontrolado de Codex | Cambios inseguros o inconsistentes. | Tareas pequeñas, diff, pruebas y revisión. |
| No documentar | Soporte difícil y dependencia del fundador. | Documentos mínimos por proyecto. |
| No ofrecer soporte | Pérdida de ingreso recurrente. | Propuesta de soporte en cada entrega. |

5. Separar bugs, ajustes, mejoras y cambios fuera de alcance.
6. Ofrecer soporte mensual en cada cierre de proyecto.
